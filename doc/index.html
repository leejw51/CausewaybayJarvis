기계가 이 맥 안에서 다 돌아간다

Causewaybay Jarvis는 온디바이스 AI 에이전트입니다. 처음부터 끝까지 Rust이고, Qwen3.8-27B(4비트)를 Apple MLX 위에서 돌립니다. 트랜스포머 자체가 Rust 포팅이지 파이썬 런타임을 감싼 바인딩이 아닙니다. 가중치를 한 번 내려받은 뒤로는 아무것도 이 기계를 떠나지 않습니다.
Causewaybay Jarvis is an on-device AI agent. Rust end to end, running Qwen3.8-27B (4-bit) on Apple MLX — the transformer itself is a Rust port, not a binding to a Python runtime. Nothing leaves the machine after the weights are downloaded once.

01 — 한눈에

다섯 개의 크레이트, 네 개의 얼굴Five crates, four faces

이 저장소는 하나의 Rust 워크스페이스와, 그 워크스페이스를 서로 다른 방식으로 들여다보는 네 개의 클라이언트로 이루어져 있습니다. 중요한 규칙은 하나뿐입니다. 토크나이저도, 채팅 템플릿도, Qwen3.5 타워도, Metal 커널도 딱 한 벌만 존재합니다. Lua CLI든 LÖVE 게임이든, 모두 같은 libjarvis를 통해 그 한 벌을 부릅니다. 다시 구현한 것은 아무것도 없습니다.

The repository is one Rust workspace plus four clients that look at it from different angles. Only one rule really matters: there is exactly one tokenizer, one chat template, one Qwen3.5 tower and one set of Metal kernels. The Lua CLI and the LÖVE game both reach that single copy through libjarvis. Nothing is reimplemented.

층은 아래로 갈수록 좁아집니다. 프런트엔드는 대화를 관리하고, rustcore는 백엔드를 모르는 채로 설정·토큰화·템플릿·스트리밍 계약을 소유하며, rustmlx만이 MLX를 압니다. 이 분리가 실제로 값을 합니다. rustcore는 MLX에 의존하지 않기 때문에 GPU도 Xcode도 없는 CI 러너에서 몇 분 만에 통과합니다.

The layers narrow as you go down. Front ends own the conversation; rustcore owns config, tokenizing, templating and the streaming contract while knowing nothing about any backend; only rustmlx knows MLX. That split pays for itself — because rustcore depends on no MLX, it builds and tests on a CI runner with neither Xcode nor a GPU in a couple of minutes.

핵심 아이디어 · The core idea

Qwen3.5는 하이브리드입니다. 64개 디코더 층 가운데 매 4번째만 보통의 어텐션이고, 나머지 48개는 gated DeltaNet—커지는 캐시 대신 고정 크기 행렬 하나를 들고 다니는 선형 어텐션입니다. 대화가 길어져도 층의 4분의 3은 메모리를 한 바이트도 더 쓰지 않습니다.

Qwen3.5 is a hybrid. Of its 64 decoder layers only every fourth is ordinary attention; the other 48 are gated DeltaNet — linear attention that carries one fixed-size matrix instead of a growing cache. However long the conversation gets, three quarters of the layers cost not one byte more.

03 — 한 턴

키를 누르고 나서 토큰이 나오기까지From a keystroke to a token

여기가 이 문서의 중심입니다. 한 번의 대화 턴은 정확히 열두 단계를 지나갑니다. 7–11번은 토큰마다 반복되는 고리이고, 나머지는 턴당 한 번씩입니다. 단계를 눌러 따라가 보세요.

This is the spine of the whole program. One conversational turn passes through exactly twelve stages; steps 7–11 are the loop that runs once per token, and the rest happen once per turn. Step through it below.

왜 이벤트 콜백인가 · Why a callback, not a channel

MLX는 GPU 큐 하나를 몹니다. 그래서 엔진은 한 스레드에서 구동되기를 기대하고, 스트리밍은 채널이 아니라 호출자에게 되돌아가는 콜백으로 구현되어 있습니다. 콜백이 Flow를 반환한다는 점이 핵심입니다. 중단은 별도의 취소 토큰이 아니라 반환값이며, 그래서 REPL의 Ctrl-C, TUI의 Esc, LÖVE의 stop 채널이 전부 같은 한 줄로 끝납니다.

MLX drives a single GPU queue, so the engine expects one thread and streaming is a callback back into the caller rather than a channel. The important part is that the callback returns a Flow: stopping is a return value, not a separate cancellation token, which is why Ctrl-C in the REPL, Esc in the TUI and the LÖVE stop channel all reduce to the same single line.

04 — 하이브리드 타워

넷 중 하나만 진짜 어텐션Only one layer in four is real attention

config.json의 full_attention_interval: 4 한 줄이 타워 전체의 모양을 정합니다. TextConfig::layer_kind(i)는 (i + 1) % 4 == 0일 때만 Full을 돌려주고, 나머지는 전부 Linear입니다. 아래 격자가 실제 64층입니다 — 위에서 아래로, 왼쪽에서 오른쪽으로.

One line of config.json — full_attention_interval: 4 — decides the shape of the whole tower. TextConfig::layer_kind(i) returns Full only when (i + 1) % 4 == 0; everything else is Linear. The grid below is the real 64, reading left to right, top to bottom.

델타 규칙 · The delta rule

DeltaNet 층은 KV 캐시 대신 [48, 128, 128] 크기의 연상 행렬 S를 들고 다닙니다. 위치마다 그 행렬을 학습된 게이트로 감쇠시키고, 지금 키가 이미 되불러오는 값을 읽어낸 다음, 그 차이만 써넣습니다.

A DeltaNet layer carries a [48, 128, 128] matrix of associations, S, instead of a KV cache. At each position it decays that matrix by a learned gate, reads back what the current key already retrieves, and writes in the difference.

그래서 Metal 커널 · Hence a Metal kernel

순차 재귀를 MLX 배열 연산으로 쓰면 위치마다 열 개쯤의 커다란 원소별 연산이 디스패치됩니다. 그래서 이 스캔만 손으로 쓴 Metal 커널로 내려갔습니다. (batch, head, value dimension)마다 simd-group 하나, 상태는 레지스터에 두고, 스텝마다 simd_sum 두 번. 층당 한 번의 디스패치입니다.

Written as MLX array operations, the sequential recurrence dispatches roughly ten large elementwise ops per position. So this one scan drops to a hand-written Metal kernel: one simd-group per (batch, head, value dimension), the state held in registers, two simd_sum reductions per step. One dispatch per layer instead.

# 프리필 처리량 / prefill throughput — M4 Max, 512-token prompt
Metal kernel   124.5 tok/s
array ops       78.7 tok/s      ← JARVIS_DELTA_KERNEL=0

두 경로는 서로를 검사한다 · The two paths check each other

JARVIS_DELTA_KERNEL=0은 이식 가능한 배열 연산 경로를 고릅니다. 테스트는 커널 경로와 배열 경로가 같은 값을 내는지 서로 대조합니다. Metal 장치가 없는 기계에서는 커널이 아예 시도되지 않고 조용히 배열 경로로 갑니다.

JARVIS_DELTA_KERNEL=0 selects the portable array-ops path, and the tests check the two against each other. On a machine with no Metal device the kernel is never attempted at all — the dispatch takes the portable route quietly rather than warning once per shape.

05 — 캐시와 메모리

대화가 길어져도 4분의 3은 그대로Three quarters of it never grows

하이브리드가 실제로 무엇을 아끼는지는 숫자로 보는 편이 빠릅니다. 완전 어텐션 층 하나는 토큰당 4 KiB를 씁니다 (KV 헤드 4개 × head_dim 256 × k와 v × bfloat16 2바이트). DeltaNet 층은 토큰 수와 무관하게 3 MiB 고정입니다 (48헤드 × 128 × 128 × float32).

The quickest way to see what the hybrid buys is in bytes. One full-attention layer costs 4 KiB per token (4 KV heads × head_dim 256 × k and v × 2 bytes of bfloat16). A DeltaNet layer costs a flat 3 MiB, whatever the length (48 heads × 128 × 128 × float32).

접두사 재사용 · Prefix reuse

후속 턴은 대개 앞 턴 프롬프트의 연장입니다. 그래서 generate는 먼저 shared_prefix(fed, ids)를 재고, 새 프롬프트가 캐시가 이미 담고 있는 것의 엄격한 연장일 때만 캐시를 재사용합니다. 아니면 전부 버리고 처음부터 프리필합니다.

A follow-up turn is usually an extension of the previous prompt. So generate measures shared_prefix(fed, ids) first and reuses the cache only when the new prompt is a strict extension of what the cache already holds. Otherwise it throws everything away and prefills from scratch.

let shared = shared_prefix(&self.fed, &ids);
let reuse  = !self.fed.is_empty() && shared == self.fed.len() && shared < ids.len();
if !reuse { self.reset(); }

이 조건이 왜 이렇게 빡빡한가에는 구체적인 이유가 있습니다. 채팅 템플릿은 기본적으로 지난 턴의 <think> 블록을 히스토리에서 떨어냅니다. 그러면 새 프롬프트는 더 이상 옛 프롬프트의 연장이 아니고, 그 순간 전체 프리필만이 올바른 선택입니다. preserve_thinking을 켜면 옛 추론을 남겨 캐시를 살릴 수 있지만, 대신 프롬프트가 계속 길어집니다.

The condition is that strict for a concrete reason: by default the chat template drops the <think> block of earlier turns from the history. The new prompt is then no longer an extension of the old one, and a full prefill is the only correct option. Turning on preserve_thinking keeps the old reasoning and so keeps the cache — at the cost of a prompt that keeps growing.

06 — C 경계

핸들은 주소가 아니다A handle is not an address

rustffi는 libjarvis를 내보냅니다. FFI가 있는 언어라면 무엇이든 이 에이전트를 몰 수 있습니다. 경계 전체를 관통하는 규칙은 네 개뿐입니다.

rustffi exports libjarvis, so anything with an FFI can drive the agent. Four rules hold everywhere across that boundary.

  • 들어가는 문자열은 NUL로 끝나는 UTF-8이고, 호출 동안만 빌려줍니다.
    Strings in are NUL-terminated UTF-8, borrowed for the call only.
  • 나오는 문자열은 호출자 소유이고 jarvis_string_free로 해제합니다. 구조화된 결과는 구조체를 더 늘리는 대신 JSON 텍스트로 나옵니다 — 그래야 양쪽이 발맞춰 갈 것이 하나 줄어듭니다.
    Strings out are owned by the caller and freed with jarvis_string_free. Structured results come back as JSON text rather than as more structs to keep in step.
  • 실패는 널 포인터거나 음수이고, 이유는 스레드 로컬인 jarvis_last_error()에 있습니다.
    Failure is a null pointer or a negative number, with the reason in the thread-local jarvis_last_error().
  • 아무것도 언와인드하지 않습니다. 모든 진입점이 패닉을 잡아 에러로 바꿉니다.
    Nothing unwinds. Every entry point catches panics and turns them into an error.

왜 토큰인가 · Why a token, not a pointer

할당 안에 태그를 써 두고 검사하는 방식은 두 가지 이유로 안 됩니다. 이미 해제된 포인터로 태그를 읽는 것 자체가 미정의 동작이고, 할당자는 그 블록을 다음 세션에게 다시 내줄 자유가 있어서 낡은 포인터가 멀쩡한 태그를 읽고 남의 세션을 가리키게 됩니다.

그래서 호출자가 쥐는 것은 아무것의 주소도 아닙니다. 오직 증가만 하는 카운터에서 나온 토큰이고, 들어올 때마다 살아 있는 목록에서 조회됩니다. 토큰은 재사용되지 않으므로, 닫힌 핸들은 프로세스가 끝날 때까지 계속 거부됩니다.

A tag written inside the allocation cannot be the check, for two reasons. Reading one back through an already-freed pointer is undefined behaviour; and the allocator is free to hand the same block out again for the next session, at which point a stale pointer reads a perfectly valid tag and starts addressing somebody else's session.

So what a caller holds is not the address of anything. It is a token from a counter that only ever goes up, looked up on the way back in. A token is never reused, so a handle that has been closed stays refused for the life of the process.

재진입 금지 · No reentrancy

한 턴은 토큰마다 호출자의 언어로 제어를 넘깁니다. 그 언어가 곧바로 되돌아 들어올 수 있는데, 바깥 호출이 아직 &mut를 쥐고 있는 그 세션에 대고 그러면 앨리어싱—미정의 동작입니다. 그래서 턴이 도는 동안 그 핸들은 busy로 표시되고, 조회는 두 번째 참조를 내주는 대신 거부합니다. 콜백 안에서의 session:close()도 같은 이유로 거부되고, 세션은 열린 채 남습니다.

A turn hands control back to the caller's language for every token, and that language can call straight back in. Doing so on the session whose &mut the outer call still holds would alias it — undefined behaviour. So while a turn runs, that handle is marked busy and the lookup refuses it rather than handing out a second reference. Closing the session from inside its own callback is refused for the same reason, and the session is left open.

/* the shape every binding mirrors — rust/rustffi/include/jarvis.h */
JarvisSession *jarvis_open(const char *alias, const char *revision, const char *repo);
int  jarvis_set_system(JarvisSession *s, const char *text);
int  jarvis_send(JarvisSession *s, const char *text, const JarvisParams *p,
                 JarvisEventFn cb, void *user);   /* blocks for the whole answer */
char *jarvis_last_json(JarvisSession *s);        /* text, reasoning, stats, stop_reason */
void jarvis_close(JarvisSession *s);

/* return non-zero from the callback to stop generating */
typedef int (*JarvisEventFn)(int kind, const char *text, size_t len,
                             uint64_t a, uint64_t b, void *user);

Ctrl-C · 인터럽트

시그널 핸들러는 대부분의 언어 런타임에 안전하게 재진입할 수 없습니다. 그래서 jarvis_interrupt_install()은 SIGINT를 넘겨받아 플래그 하나만 세웁니다. 토큰 사이에서 그 플래그를 읽고 콜백이 0이 아닌 값을 돌려주는 것 — 그게 메커니즘의 전부입니다.

A signal handler cannot safely re-enter most language runtimes. So jarvis_interrupt_install() takes over SIGINT and sets a flag, and nothing else. Reading that flag between tokens and returning non-zero from the callback is the entire mechanism.

07 — 클라이언트

같은 모델, 네 개의 얼굴One model, four faces

네 클라이언트는 같은 슬래시 명령을 공유합니다 — /help /reset /think /stats /system. 손에 익은 것이 그대로 넘어가라는 뜻입니다.

All four share the same slash commands — /help, /reset, /think, /stats, /system — so muscle memory carries across.

기본 명령입니다. REPL, 원샷 run, pull, info, models, bench. MlxEngine과 메시지 목록을 따로 들고 있습니다 — Rust 프런트엔드는 그럴 수 있으니까요. 스트리밍은 repl.rs의 stream_turn이 담당하고, 추론이 끝나고 답이 시작되는 자리에 빈 줄이 정확히 하나 들어가도록 개행을 셉니다.

The default command: a REPL, one-shot run, plus pull, info, models and bench. It keeps the MlxEngine and the message list apart — a Rust front end can. Streaming lives in stream_turn in repl.rs, which counts newlines so the gap between reasoning and answer is exactly one blank line however the model spaced it.

rustcli                                  # the REPL
rustcli run "why is the sky blue?"
echo "summarise this" | rustcli run     # reads stdin
rustcli --model qwen3.8:27b-mlx-8bit chat
rustcli bench                            # prefill and decode throughput

ratatui 위의 전체 화면 채팅. 생성은 메인 스레드에서 돌고 스트리밍 콜백 안에서 다시 그립니다. 프로그램 전체가 단일 스레드로 남으면서 — MLX가 선호하는 바입니다 — 토큰마다 다시 칠하고 Esc에 반응합니다.

대화 기록을 일부러 두 벌 들고 있습니다. messages는 채팅 템플릿이 보는 것이고, blocks는 화면이 보여주는 것입니다. 추론이 접히는 자체 블록으로 그려지는 반면 템플릿은 그것을 어시스턴트 턴의 일부로 취급하기 때문에 둘이 갈라집니다.

Full-screen chat on ratatui. Generation runs on the main thread and redraws from inside the streaming callback — which keeps the whole program single-threaded, as MLX would prefer, while still repainting on every token and staying responsive to Esc.

The transcript is kept twice on purpose: messages is what the chat template sees, blocks is what the screen shows. They diverge because reasoning is rendered as its own collapsible block while the template treats it as part of the assistant turn.

# enter sends · Esc stops · Ctrl-R resets
# Ctrl-T shows or hides reasoning · Ctrl-K turns thinking off
rusttui --no-think --temperature 0

LuaJIT의 ffi로 libjarvis를 부르는 채팅 클라이언트입니다. jarvis/ffi.lua는 헤더를 손으로 옮겨 적은 cdef입니다 — LuaJIT은 C는 파싱해도 전처리기는 못 하니까요. 그래서 라이브러리가 자기 ABI 버전과 구조체 크기를 보고하고, 어긋나면 로드 시점에 거부합니다. 세 번의 호출 뒤 망가진 구조체로 드러나는 대신에요.

실패할 수 있는 것은 예외를 던지지 않고 nil, message를 돌려줍니다. 채팅 루프는 문제를 찍고 계속 가면 되니까요.

A chat client calling libjarvis through LuaJIT's ffi. jarvis/ffi.lua is a cdef that mirrors the header by hand — LuaJIT parses C but not the preprocessor. So the library reports its own ABI version and struct sizes and the module refuses to load when they disagree: a mismatch is caught at load, not as a corrupt struct three calls later.

Anything that can fail returns nil, message rather than raising, because a chat loop wants to print the problem and carry on.

local jarvis  = require("jarvis")
local session = assert(jarvis.open("qwen3.8:27b-mlx"))
session:set_system("You are Jarvis.")

local reply = assert(session:send("why is the sky blue?", jarvis.params(),
  function(kind, text)
    if kind == "token" then io.write(text) io.flush() end
  end))

print(reply.stats.decode_tps, reply.stop_reason)

720×405 화면, 슈퍼패미컴 팔레트, 손으로 그린 6×8 폰트, MSX2 부팅 시퀀스와 브라운관. 모델은 밤의 보헤미아 거리에 선 기사이고, 일부러 맨몸으로 그려져 있습니다 — 갬비슨과 타바드, 투구, 기대선 검, 판금은 어디에도 없습니다.

그를 둘러싼 소켓 고리가 하니스입니다. 메모리, 도구, 검색, 플래너, 크리틱, 샌드박스, 눈, 목소리. 이렇게 그리는 이유는 그것이 사실이기 때문입니다. 언어 모델은 텍스트를 이어 붙이는 물건이고, 그것을 에이전트로 만드는 모든 것은 바깥에 덧대어집니다. 그리고 모듈들은 전부 비어 있습니다. 클라이언트가 자기 하니스 화면에서 그렇게 말합니다. 있는 것은 형태입니다 — 모듈이 자신을 등록하고, 소켓을 하나 받고, 턴 안에서 진짜 일이 들어갈 지점마다 호출됩니다.

A 720×405 screen, a Super Famicom palette, a hand-drawn 6×8 font, an MSX2 boot sequence and a cathode ray tube. The model is a knight standing in a Bohemian street at night, drawn deliberately bare — gambeson, tabard, helm and the sword he leans on, and no plate anywhere.

The ring of sockets around him is the harness: memory, tools, retrieval, a planner, a critic, a sandbox, an eye, a voice. Drawing it this way is true to the thing: a language model continues text, and everything that makes it an agent is strapped on around it. And the modules are all empty — the client says so on its own harness screen. What exists is the shape: a module declares itself, takes a socket, and is called at every point in a turn where the real work would go.

-- src/harness.lua is a registry; the ring re-lays itself out
harness.register{
  id = "memory", name = "MEMORY", glyph = "book", slot = "cyan",
  key = "1", blurb = "keeps what was said, and what it meant",

  on_turn_start = function(module, ctx)
    ctx.prompt = recall(ctx.prompt)      -- rewriting it is the point
  end,
  on_turn_end = function(module, ctx) remember(ctx.reply, ctx.stats) end,
}

훅은 턴이 부르는 순서대로 on_equip, on_turn_start, on_prefill, on_reasoning, on_token, on_turn_end, on_error, on_remove입니다. 훅이 예외를 던지면 잡아서 모듈을 쾅 하고 떨어뜨리고 턴은 계속 갑니다 — C ABI가 Lua 콜백과 맺은 것과 같은 거래입니다.

The hooks, in the order a turn fires them: on_equip, on_turn_start, on_prefill, on_reasoning, on_token, on_turn_end, on_error, on_remove. A hook that raises is caught, the module is knocked off with a bang, and the turn carries on — the same bargain the C ABI makes with a Lua callback.

스레드 세 개의 채널 · Three channels, one worker

jarvis_send는 답이 끝날 때까지 블록하고 그 안에서 토큰 콜백을 쏩니다. 초당 60프레임을 그려야 하는 스레드와 같이 살 수 없습니다. 그래서 모델은 worker.lua에서 자기 스레드를 갖고, 게임과는 세 개의 채널로만 이야기합니다.

jarvis_send blocks for as long as an answer takes and fires its token callback from inside itself, so it cannot share a thread with sixty frames a second. The model lives on its own thread in worker.lua and talks to the game over three channels.

jarvis.cmd    main → worker    {op = "open"|"send"|"reset"|"system"|"quit"}
jarvis.evt    worker → main    {ev = "ready"|"token"|"done"|"error"|…}
jarvis.stop   main → worker    anything at all means "stop this turn"

창을 닫는 것은 두 단계다 · Quitting is a two-step

MLX의 Metal 장치는 C++ 전역이고, 프로세스가 끝날 때 메인 스레드에서 도는 정적 소멸자가 파괴합니다. 그때 워커가 아직 jarvis_send 안에 있으면 해제된 컴퓨트 파이프라인이 드라이버에 넘어가고 프로세스는 나가는 길에 SIGSEGV로 죽습니다. 그래서 love.quit은 첫 번째 종료를 거부하고, 턴을 중단시키고, 워커에게 닫으라고 한 뒤, 그 스레드가 실제로 사라진 다음에야 종료를 받습니다 — 6초 상한과 함께. 가설이 아니라, 기다림을 넣기 전에는 세 번 중 두 번 크래시했습니다.

MLX's Metal device is a C++ global destroyed by the static destructors that run on the main thread as the process exits. If the worker is still inside jarvis_send when that happens, it hands a freed compute pipeline to the driver and the process dies with SIGSEGV on the way out. So love.quit refuses the first quit, interrupts the turn, asks the worker to close, and takes the quit only once that thread has actually gone — with a six-second cap. This was not theoretical: before the wait, quitting crashed two runs in three.

08 — 설정

한 줄에 하나씩One object per line

설정 전체가 config.jsonl입니다. 줄마다 {"key": …, "value": …} 하나. 어떤 언어에서도 읽기 쉽고, git에서 줄 단위로 깔끔하게 diff됩니다. 없는 키는 기본값으로 떨어지므로 부분적인 파일도 괜찮습니다.

All configuration is config.jsonl — one {"key": …, "value": …} per line. Trivial to read from any language, and it diffs line-by-line in git. Anything absent falls back to a default, so a partial file is fine.

{"key": "model",      "value": {"alias": "qwen3.8:27b-mlx", …}}
{"key": "generation", "value": {"max_tokens": 2048, "temperature": 0.7,
                              "top_p": 0.95, "top_k": 20, "min_p": 0.0,
                              "repetition_penalty": 1.05, …}}
{"key": "thinking",   "value": {"enabled": true, "effort": "low", "show": true}}
{"key": "runtime",    "value": {"wired_limit_gb": 0, "kv_bits": 0}}

어디서 찾는가 · Where it is found

JARVIS_CONFIG → 작업 디렉터리에서 위로 올라가며 → 바이너리 옆 → 컴파일된 사본. 이 걸어 올라가기는 파일시스템 루트까지 가므로 사용자가 통제하지 않는 디렉터리(/tmp 같은)를 지나갑니다. 설정은 어떤 체크포인트를 내려받아 실행할지를 정하므로, 남이 썼을 수도 있는 후보는 신뢰하는 대신 건너뜁니다 — 다른 사용자 소유이거나 world-writable이면 이유를 찍고 지나갑니다. group-writable은 일부러 허용합니다. 공유 umask 아래의 664 파일은 평범하고, 여기서의 위협은 무관한 사용자니까요.

JARVIS_CONFIG, then walking up from the working directory, then beside the binary, then the compiled-in copy. That walk climbs to the filesystem root, so it can pass through directories the user does not control — /tmp and friends. A config decides which checkpoint is downloaded and run, so a candidate someone else could have written is skipped rather than trusted: owned by another user, or world-writable, and it is passed over with the reason printed. Group-writable is deliberately allowed — a 664 file under a shared umask is ordinary, and the threat here is an unrelated user.

별칭에서 저장소로 · From alias to repository

별칭은 이 프로젝트가 이미 쓰던 Ollama식 이름(qwen3.8:27b-mlx)을 따르지만 언제나 Hugging Face 저장소로 해석됩니다. MLX 형식 가중치가 실제로 사는 곳이 거기이기 때문입니다. org/name 형태의 날것도 그대로 받습니다.

자기 자신이 아니라 원본과 대조한다Checked against the reference, not against itself

GPU가 없는 척하기 · Pretending the GPU is not there

JARVIS_NO_METAL=1은 기계에 GPU가 없는 것처럼 굽니다. MLX는 CPU 장치로 옮겨 가고, 진짜 Metal 장치가 필요한 테스트는 실패하는 대신 그렇게 말하며 스스로 건너뜁니다. Metal이 없다고 보고하는 것만으로는 부족합니다 — MLX가 여전히 GPU 스트림을 기본으로 잡아 배열 경로가 조용히 그 위에 남기 때문에, 이 모의는 기본 장치도 CPU로 고정합니다. Metal 없는 기계가 MLX에서 받는 것이 정확히 그것이므로, 이 시뮬레이션은 그럴듯한 게 아니라 충실합니다.

GPU 없는 러너는 이 코드를 돌릴 수 없으니, GPU 없는 경로를 확인할 수 있는 유일한 방법은 GPU가 있는 기계에서입니다. 96개 중 91개가 그 모드에서 여전히 돕니다. 건너뛰는 다섯은 커스텀 커널 자체와, 커널을 배열 경로와 대조하는 셋 — GPU 없는 실행이 보증할 수 없는 바로 그것들입니다.

JARVIS_NO_METAL=1 pretends the machine has no GPU: MLX moves to the CPU device and the tests that need a real Metal device skip themselves, saying so, rather than failing. Reporting no Metal is not enough on its own — MLX would still default to the GPU stream and the array paths would quietly stay on it, so the mock also pins the default device to the CPU. That is what a machine without Metal gets from MLX anyway, so the simulation is faithful rather than merely plausible.

A GPU-less runner cannot run this code, so the only way to check the GPU-less path is from a machine that does have one. 91 of the 96 tests still run in that mode; the five skipped are the custom kernel and the three that check it against the array-ops path — exactly the ones a GPU-less run cannot vouch for.

MLX는 GPU 큐 하나를 몰기 때문에 그것을 건드리는 테스트는 --test-threads=1로 돌아야 합니다. Makefile이 어디서나 그 플래그를 넘깁니다. CI는 두 레인입니다 — core는 MLX에 의존하지 않아 Xcode도 GPU도 없이 몇 분이면 끝나고, workspace는 mlx-sys가 MLX와 Metal 셰이더를 소스에서 컴파일하는 값을 치릅니다(Metal 컴파일러는 필요하지만 Metal 장치는 필요 없습니다).

MLX drives a single GPU queue, so tests that touch it must run with --test-threads=1; the Makefile passes that everywhere. CI runs in two lanes: core is the quick one — rustcore depends on no MLX, so it needs neither Xcode nor a GPU — and workspace is the real gate, paying for mlx-sys to compile MLX and its Metal shaders from source (which needs the Metal compiler from Xcode, but no Metal device).

아직 없는 것 · Not there yet

  • 텍스트 전용. 체크포인트 안의 비전 타워는 로드하지 않습니다.
    Text only. The vision tower in the checkpoint is not loaded.
  • 한 번에 하나의 시퀀스. 배칭이 없습니다.
    One sequence at a time. There is no batching.
  • 도구 호출 없음. 템플릿은 지원하고 RenderOptions::tools는 프롬프트까지 닿지만, <tool_call>을 되파싱하는 것이 아직 없습니다 — LÖVE 클라이언트의 하니스 소켓이 아무것에도 연결되지 않은 이유이기도 합니다.
    No tool calling yet. The template supports it and RenderOptions::tools reaches the prompt, but nothing parses a <tool_call> back out — which is also why the LÖVE client's harness sockets are wired to nothing.
  • MTP 헤드 무시. MTP 체크포인트의 다중 토큰 예측 헤드는 쓰지 않습니다.
